# Execd 设计框架（Go）

## 1. 项目目标

实现一个基于 Go 的常驻服务 Execd，运行于 Runtime 基于 Docker 创建的 Sandbox 容器内部，作为 Sandbox 内部的执行服务，通过 HTTP API 向外部调用方提供统一的环境配置、文件操作、命令执行及任务管理接口。Execd 默认以 `/workspace` 作为工作区域，支持执行超时、任务取消、状态查询及相关资源清理。

**核心原则：**
- Sandbox 容器及基础工作区域由 Runtime 负责创建和准备，Execd 负责工作区域内的文件管理及命令执行。
- Execd 通过 HTTP API 对外提供标准化的容器内部操作接口，支持外部调用方直接访问并获取执行结果。
- Runtime 负责 Sandbox 的生命周期管理、Execd 的部署和访问端点配置，以及容器状态查询；容器运行状态及健康状态由 Docker Daemon 统一维护，Runtime 通过 Docker Go SDK 获取相关信息。
- Execd 通过 Docker HEALTHCHECK 机制提供健康检查能力，由 Docker Daemon 定期检查并维护容器健康状态。
- Runtime 不参与常规文件操作和命令执行结果的转发。
- 文件操作与命令执行相互独立，共享 Sandbox 内部文件系统，不存在强依赖关系。
- 所有操作需要考虑超时、异常处理和幂等性。
- 命令执行优先采用参数数组（argv）传递命令及参数，避免不必要的 Shell 拼接和注入风险。
- 前台与后台执行复用底层命令执行逻辑，支持任务状态管理、日志收集和取消。

## 2. 核心功能

### 2.1 环境配置
- 读取 Runtime 在容器创建时提供的默认环境变量配置（如 `PATH`、`VIRTUAL_ENV` 等），作为命令执行的基础环境。
- 默认工作目录为 `/workspace`，由 Runtime 负责准备。
- 命令请求可通过 `cwd` 和 `env` 为单次执行指定工作目录与环境变量，请求级配置覆盖默认配置。
- Execd 不提供全局环境变量修改接口；运行时依赖（如 Python 环境 `/workspace/.venv`）通过命令执行能力安装，不单独设计一套执行机制。

### 2.2 文件操作
提供 Sandbox 工作区域（`/workspace`）内的文件和目录管理能力，支持文件上传、下载、目录创建、目录查询及文件删除，实现外部调用方与 Sandbox 之间的文件传输和管理。文件操作通过 Execd 提供的 HTTP API 对外开放，由 Execd 直接操作 Sandbox 内部文件系统，并通过 HTTP 请求和响应完成文件传输。文件操作仅负责文件及目录的读写、传输和管理，不负责文件内容解析、业务处理或程序执行；与命令执行模块相互独立，不依赖命令执行能力实现。

### 2.3 命令执行

支持在指定 Sandbox 的工作区域（`/workspace`）内执行命令，通过请求参数指定执行模式：

- **前台执行（Foreground）**：适用于执行时间较短、需要立即获取结果的命令。Execd 等待命令执行结束，并返回标准输出（stdout）、标准错误（stderr）和退出码（exit_code）。支持设置执行超时时间，避免长时间占用请求连接。命令执行结束后释放相关执行资源，不长期保留任务记录。
- **后台执行（Background）**：适用于耗时较长的任务。Execd 启动命令后立即返回唯一的任务 ID（execution_id），不等待任务结束。后台任务交由任务管理模块统一管理。

前台与后台执行复用底层命令执行逻辑，支持命令参数、工作目录、环境变量及执行超时等配置。

### 2.4 任务管理

提供后台命令执行任务的统一管理能力，维护任务信息及生命周期，支持任务状态跟踪、执行日志收集、任务取消、执行超时、基本的并发控制，以及任务结束后的资源清理。

- 调用方可通过任务 ID（execution_id）查询任务状态、执行日志、退出码及最终结果。

- 任务信息支持持久化，包括任务标识、执行命令、任务状态、执行时间、日志及最终结果等。Execd 重启后恢复已有任务记录，并对重启前未正常结束的任务进行状态修正，不自动恢复已中断的命令执行。

### 2.5 状态与信息查询

提供 Sandbox 运行状态及相关信息的查询能力，区分容器级状态与容器内部运行信息：

- **容器级状态**：由 Docker Daemon 统一管理，通过 Docker HEALTHCHECK 机制定期检查 Execd 服务健康状态，并维护容器健康状态（starting、healthy、unhealthy）。Runtime 通过 Docker Go SDK 获取 Sandbox 容器的运行状态及健康状态。
- **容器内部信息**：由 Execd 提供 HTTP API，支持查询运行环境配置信息、工作区域（`/workspace`）内的文件及目录信息，以及后台命令执行任务的状态、执行日志和最终结果。

Runtime 根据需要通过 Docker API 和 Execd HTTP API 分别获取容器级状态及内部运行信息。

### 2.6 进程与信号管理
Execd 作为 Docker Sandbox 容器的主进程（PID 1），负责处理 Runtime 通过 Docker API 发起的容器停止操作所触发的进程信号，实现优雅退出及资源清理。

- 优雅退出：接收到 SIGTERM 等终止信号时，停止接受新的执行请求，取消或终止正在运行的后台任务，完成必要的资源清理后退出。

- 异常退出：Execd 异常退出或容器被强制终止时，由 Runtime 和 Docker 负责容器生命周期管理；Execd 再次启动后，根据持久化任务记录修正未正常结束的任务状态。

## 3. 安全与资源管理

- 对并发执行任务数量进行限制，避免过多任务占用系统资源。
- 对文件上传大小、文件操作范围及命令执行输出大小进行必要限制。
- 对命令、环境变量、工作目录及文件操作路径进行校验，防止非法输入和路径越权。
- 对命令执行设置超时时间，并支持任务取消，避免任务无限期运行。
- 对命令执行输出进行必要的大小限制，避免长时间运行的任务产生大量日志，导致内存或磁盘资源被占用。

## 4. 验证要求

- **环境配置验证**：验证工作目录和环境变量配置是否正确生效，未指定工作目录时是否默认使用 `/workspace`。
- **文件操作验证**：验证文件上传、下载、目录创建、查询及删除等功能是否正常，确保文件传输完整。
- **命令执行验证**：验证前台与后台执行模式是否正常，确保执行结果、退出码及任务 ID 返回正确，并支持执行超时和任务取消。
- **任务管理验证**：验证后台任务的状态跟踪、日志收集、结果查询及持久化能力，确保 Execd 重启后任务记录能够正确恢复。
- **状态与信息查询验证**：验证 Docker HEALTHCHECK 能否正确检测 Execd 服务状态，以及 Runtime 能否获取容器运行状态和健康状态；验证 Execd 内部信息查询接口是否正常。
- **进程与信号管理验证**：验证 Execd 对终止信号的处理能力，确保容器停止时能够正常退出并完成必要的资源清理。
- **安全与可靠性验证**：验证文件路径校验、命令执行限制、并发控制及异常处理机制，确保系统在超时、取消和异常退出等情况下能够合理释放资源。
